# Offline caching (service worker)

The service worker is generated by `vite-plugin-pwa` (`generateSW`, `registerType: 'autoUpdate'`,
`skipWaiting` + `clientsClaim`, so a new worker takes over open tabs as soon as it is installed and
`autoUpdate` reloads the page). The rules
live in `apps/web/src/pwa/runtimeCaching.ts` (pure data, unit-tested) and are fed to workbox from
`apps/web/vite.config.ts`. Ticket: #51 (a missing GLB/thumbnail must never crash the page).

| What | URL | Strategy | Cache | Stored when |
| --- | --- | --- | --- | --- |
| App shell | build output | precache (`cleanupOutdatedCaches`, files up to 4 MiB) | `workbox-precache-v2-*` | build time |
| Bank files (hashed, immutable GLB/WebP) | `/bank/assets/*` | `CacheFirst` | `hsw-bank-assets-v1` (max 1200 entries, purged on quota error) | HTTP `200`, not `text/html` |
| Bank index, search index | `/api/bank/index`, `/api/bank/search-index` | `StaleWhileRevalidate` | `hsw-bank-index-v1` | HTTP `200`, not `text/html` |

## Never cached

- A `200 text/html` body (a server that falls back to the SPA shell for an unknown path would
  otherwise poison an immutable entry).
- URLs with a query string or fragment under `/bank/assets/` (they bypass the rule and hit the network).
- Any non-200 response (404 `asset_not_found`, 503 "bank not built", 5xx) and opaque responses: a
  failed revalidation never replaces a good cached copy.
- `POST /api/bank/elements/:id/variant` and every other `/api/*` request (they fall through to the
  network), SSE and WebSocket traffic.
- Navigations to `/api/*` and `/bank/*` never fall back to the app shell (`navigateFallbackDenylist`).

## Behaviour

- A bank file that was fetched once is served from cache even if the network is down or the server
  later answers 404 for that name (hash names are immutable, so the cached bytes are still right).
- The index is served instantly from cache (also offline) and refreshed in the background; the next
  page load sees the new copy (`loadBank()` memoises its first result within a page).
- Stale-index tab: when the bank was rebuilt and an old tab asks for an asset that was never cached
  and no longer exists, the bank server answers 404 `{"error":"asset_not_found","indexHash":...}` (not
  cached; that contract is implemented by the bank slice of #51). The index is revalidated in the background and replaced; the next page load sees the
  fresh element list. Assets of elements the user already viewed keep working from cache.

## Clearing

In DevTools: Application → Cache Storage, or from the console:

```js
await caches.delete('hsw-bank-assets-v1');
await caches.delete('hsw-bank-index-v1');
```

Bumping the `-v1` suffix in `runtimeCaching.ts` abandons the old cache (it is not deleted
automatically: delete it as above).

## Verifying

- `bun test apps/web/src/pwa` checks matchers, strategy names, and that only a non-HTML `200` is
  cacheable. When `apps/web/dist/sw.js` exists and is newer than `runtimeCaching.ts` and
  `vite.config.ts` (i.e. after `bun run build`) the same file asserts the built worker contains the
  runtime routes; otherwise that test is skipped.
- Service workers need a secure context: `https://` or `http://localhost` / `127.0.0.1`. On a plain-http
  LAN preview URL the worker does not register and none of the above applies.

## Known limits

- Stale-while-revalidate means the first page load after a bank rebuild still receives the previous
  index (the fresh copy lands in the cache and shows on the next load). `loadBank()` does not
  re-fetch within a page.
- On the very first visit the worker is not yet in control: requests made before it claims the page
  bypass it and are not cached.
- One `hsw-bank-assets-v1` cache holds thumbnails and GLBs of every element (up to three entries
  each) and is capped at 1200 entries (least recently used goes first).
- URLs are matched without anchoring, so a same-origin GET whose full URL merely ends in
  `/bank/assets/...` (for example inside a query string) would also match.
