# hsw-editor HTTP API

Base URL `http://127.0.0.1:8794` (port in `~/.config/hsw-editor/config.json`). JSON in, JSON out, UTF-8.
The wall/op types are defined once, in `packages/core` (`schema.ts`, zod); every request body below is
validated against them. Import `applyOp`, `OpSchema`, `parseWall`, `opJsonSchema()` instead of re-modelling.

## Security

- The daemon binds loopback only. A request is refused with `403 forbidden_host` unless its `Host` header is
  `127.0.0.1`, `localhost` or `[::1]` (DNS-rebinding guard), and with `403 forbidden_origin` if an `Origin` header is
  present that is not the same origin or one of `HSW_EDITOR_ALLOWED_ORIGINS` (default: the Vite dev server,
  `http://127.0.0.1:5194`, `http://localhost:5194`). Requests without `Origin` (CLI, agents, curl) pass.
- No CORS headers are ever sent (no `Access-Control-Allow-*`); cross-origin browser reads are impossible.

## Conventions

- Ids match `[A-Za-z0-9][A-Za-z0-9_.-]{0,63}`; omitted item/photo/model ids are generated by the server.
- **Wall coordinates**: millimetres; x right, y up, z out of the wall; board lower-left corner = origin. Cell centres:
  `x = (col + .5) * colPitch`, `y = (row + .5 + (col odd ? .5 : 0)) * rowPitch` (HSW: 20.4382 x 23.6 mm). Rotations in
  degrees, `rotZ` about the wall normal (holders are expected at multiples of 60; other angles are allowed and raise a `rotation_off_symmetry` warning). See `packages/core/src/grid.ts`.
- `rev` is a monotonic integer per wall: +1 for every op that changes the wall (undo and redo included). An op that
  changes nothing does **not** bump it.
- Actor: `{ "kind": "human" | "agent" | "cli", "name"?: string }`, recorded with every history entry and SSE event.
  Taken from the `actor` body field; defaults to `{kind:"human"}` (UI) and `{kind:"cli"}` (`hsw-editor wall ...`).
- Errors: `{ "error": { "code": string, "message": string, "details"?: ... } }` with the status below.

| Status | `error.code`                                       | Meaning                                                                    |
| ------ | -------------------------------------------------- | -------------------------------------------------------------------------- |
| 400    | `invalid_json`, `invalid_body`, `invalid_id`       | Malformed JSON / body does not match the schema (`details`: list of issues) |
| 403    | `forbidden_host`, `forbidden_origin`               | Guard rejected the request                                                 |
| 404    | `not_found`, `wall_not_found`, `asset_not_found`, `request_not_found`, `unknown_job_kind`, `job_not_found` | Unknown route / wall / file / request / job |
| 409    | `rev_conflict`                                     | `baseRev` is stale; body also has `wall` (current) and `currentRev` (`PUT /api/settings`: `settings` instead of `wall`) |
| 409    | `wall_exists`                                      | `POST /api/walls` with an id that is taken                                 |
| 409    | `nothing_to_undo`, `nothing_to_redo`               | Empty undo/redo stack                                                      |
| 409    | `undo_conflict`, `redo_conflict`                   | The stored inverse/op no longer applies to the current wall                |
| 409    | `request_closed`                                   | The input request was already answered or cancelled                        |
| 413    | `payload_too_large`                                | Upload above the limit (photos 40 MB, models 100 MB; settings 256 KiB)     |
| 415    | `unsupported_media_type`                           | Not a JPEG/PNG/WebP photo, not a binary glTF (`.glb`) model                |
| 422    | `heic_conversion_failed`                           | A HEIC photo could not be converted to JPEG (needs `uv` and, once, network) |
| 501    | `heic_converter_unavailable`                       | HEIC upload but `uv` is not installed                                       |
| 422    | `op_failed`                                        | Op refused by the reducer: `details` = `{ opIndex?, code }` (see below)    |
| 422    | `invalid_request`                                  | An input request points at an item/photo/model that is not on the wall     |
| 500    | `internal`                                         | Bug; the wall on disk is still consistent                                  |

Reducer codes (`details.code`): `item_not_found`, `item_exists`, `item_locked`, `photo_not_found`, `photo_exists`,
`model_not_found`, `model_exists`, `invalid_op`. A request with several ops is atomic: one refused op = nothing applied.

## Walls

| Method & path             | Body / query                                                      | Response                                    |
| ------------------------- | ----------------------------------------------------------------- | ------------------------------------------- |
| `GET /api/walls`          |                                                                   | `{ walls: WallSummary[] }`                  |
| `POST /api/walls`         | `{ name, id?, board? (partial; defaults 48x32 HSW), actor? }`     | `201 { wall, warnings, canUndo, canRedo }`  |
| `GET /api/walls/:id`      |                                                                   | `{ wall, canUndo, canRedo, warnings }`      |
| `DELETE /api/walls/:id`   |                                                                   | `{ ok: true, trashedTo }` (moved to `walls/.trash/`, never unlinked) |
| `GET /api/walls/:id/history` | `?since=<rev>&limit=<n>`                                       | `{ entries: HistoryEntry[] }` (rev > since) |
| `GET /api/walls/:id/export`  |                                                                | `{ format: "hsw-editor-wall", version: 1, wall, history }` |

`WallSummary = { id, name, rev, items, photos, models, updatedAt }`.
`HistoryEntry = { rev, ts, actor, kind: "create" | "op" | "undo" | "redo", op, inverse, ref?, label? }` — `op` is
what was applied to the wall at `rev`; for `undo`/`redo`, `ref` is the rev being undone/redone.

## Ops

`POST /api/walls/:id/ops`

```json
{ "ops": [ { "type": "moveItem", "id": "i-1", "to": { "cell": { "col": 4, "row": 2 } } } ],
  "baseRev": 17, "actor": { "kind": "agent", "name": "omp" }, "label": "optional batch label" }
```

- `baseRev` (optional): if present and not equal to the wall's current `rev` the request fails with `409 rev_conflict`
  and nothing is applied. Omit it to apply on top of whatever is current (last writer wins).
- More than one op is wrapped into a single `batch` op: one rev, one history entry, one undo step.
- Response `200 { rev, changed, op, inverse, wall, warnings }`. `changed:false` = every op was a no-op (nothing
  written, `rev` unchanged). `warnings` are geometry/reference problems (`cell_collision`, `out_of_board`,
  `cell_out_of_board`, `rotation_off_symmetry`, `missing_parent`, `parent_not_holder`, `slot_collision`,
  `slot_without_parent`, `missing_photo`, `missing_model`); they never block. `out_of_board` is about the item's origin and is
  not raised for a tool hung on a holder whose origin lies within 1000 mm of that holder: it may overhang the board edge
  (physics judges how it hangs).

Op types (`packages/core/src/schema.ts`; JSON schema via `opJsonSchema()`): `addItem`, `removeItem`, `moveItem`,
`rotateItem`, `setParams`, `setVariant`, `lock`, `attachItem`, `addPhoto`, `removePhoto`, `setCalibration`, `setBoard`,
`rename`, `addModelRef`, `updateModelRef`, `removeModelRef`, `batch`. Locked items refuse every op except `lock`.

`attachItem { id, parentId: Id | null, slot?: int | null }` hangs a tool on a holder (sets `parentId` and the 0-based
mount `slot`) or, with `parentId: null`, detaches it (a `slot` given with `null` is kept: it restores a stored
slot-without-parent item on undo). Only tools hang. The parent is not validated: an id that does not exist is
accepted and reported as `missing_parent`, a non-holder as `parent_not_holder` — a deliberate trade-off: removing a holder leaves its tools pointing at
it, and undoing a later re-attach must be able to restore exactly that state. It does not move the tool: pose
changes are separate `moveItem`/`rotateItem` ops (the `@hsw-editor/compat` planners batch them so one undo reverts
the whole hang, and carry hung tools when their holder moves, rotates or is removed).

`POST /api/walls/:id/undo` and `/redo` — body `{ baseRev?, actor? }` -> same response as ops. Undo/redo is a single
linear stack across all actors: it applies the stored inverse of the newest not-yet-undone op.

## Assets

- `POST /api/walls/:id/photos` — `multipart/form-data`: `file` (JPEG/PNG/WebP/AVIF/HEIC; EXIF orientation is applied and HEIC/AVIF converted, so stored pixels are upright), optional `name`, `actor` (JSON string).
  Stores `photos/<id>.<ext>`, applies an `addPhoto` op. `201 { photo, rev, wall }`.
- `GET /api/walls/:id/photos/:photoId/file` — the image (`cache-control: private, max-age=31536000, immutable`).
- `POST /api/walls/:id/models` — `multipart/form-data`: `file` (binary glTF, `.glb`), optional `label`, `forItemId`, `actor`.
  Stores `models/<id>.glb`, applies `addModelRef` (status `candidate`). `201 { model, rev, wall }`.
- `GET /api/walls/:id/models/:modelId/file` — the model file.
- Model references without a file (found online, bank candidates) are plain `addModelRef` / `updateModelRef` ops.
- A **cleaned variant** of a wall photo is a second `Photo` of the same wall: `view: "clean"`, `origin: "generated"`, `cleanOf: <original id>`,
  `backend: "basic" | "omp" | "chatgpt-browser"`, `cleanFootprint` (the board footprint it was made for, `1152x1536@12:x,y;x,y;x,y;x,y` (photo size, margin in mm, corner pixels),
  `footprintSignature` of `@hsw-editor/overlay`). The file lives in `photos/derived/clean-*.jpg` and is served like any photo. It has no
  calibration of its own (the original's applies), the original is never changed, and a clean is an ordinary `addPhoto` (+ `removePhoto`
  of the variant it replaces) batch, so undo/redo work. Clients list originals only (`cleanOf` absent).

## Live events (SSE)

`GET /api/walls/:id/events` (`text/event-stream`). Each frame has `id: <rev>`.

| `event`     | `data`                                   | When                                                                  |
| ----------- | ---------------------------------------- | --------------------------------------------------------------------- |
| `snapshot`  | `{ wall }`                               | On connect without `Last-Event-ID`/`?since`, or when resume is impossible |
| `op`        | a `HistoryEntry` (`rev`, `actor`, `op`…) | Every applied op, undo and redo, in rev order                         |
| `heartbeat` | `{ rev }`                                | Every 15 s; also lets a client detect that it missed revs             |
| `deleted`   | `{}`                                     | The wall was deleted; the stream then closes                          |
| `request_input` | `{ request }`                        | An input request was opened; open ones are re-sent after every (re)connect (no `id`) |
| `request_resolved` | `{ id, status, answer? }`         | A request was answered or cancelled (no `id`)                         |

Resume: reconnect with `Last-Event-ID: <rev>` (EventSource does this automatically) or `?since=<rev>`; the server
replays every entry with a greater rev, then continues live. If `since` is ahead of the server's rev a `snapshot` is
sent instead. Clients apply `op` events with the same `applyOp` reducer from `packages/core` and resync (refetch the
wall) if they see a gap in `rev`.

## Input requests

An agent or job asks the human a question while it works; the UI renders a widget, the human answers, the asker gets the
answer. Requests never change the wall and are not in the undo history (the UI applies the wall edits itself via `/ops`
first, then answers). Persisted in `walls/<id>/requests.json`. Types: `packages/core/src/request.ts`.

`InputRequest = { id, kind, status: "open" | "answered" | "cancelled", itemId?, photoId?, title?, prompt?, payload, createdBy, createdAt, resolvedBy?, resolvedAt?, answer? }`

| `kind`        | `payload`                                                                                                  |
| ------------- | ---------------------------------------------------------------------------------------------------------- |
| `dimension`   | `{ fields: [{ key, label?, unit: "mm", min?, max?, fitted?, suggested? }] }`                               |
| `variant`     | `{ candidates: [{ id, bankId?, label, score? }] }`                                                         |
| `compare`     | `{ modelRefIds: [Id, ...] }` (>= 2 entries of `wall.models`)                                               |
| `calibration` | `{ photoId, mode: "two-point" \| "grid" }`                                                                 |

| Method & path                              | Body / query                    | Response                                         |
| ------------------------------------------ | ------------------------------- | ------------------------------------------------ |
| `POST /api/walls/:id/requests`             | `{ request: { kind, payload, itemId?, photoId?, title?, prompt? }, actor? }` (default actor `{kind:"agent"}`) | `201 { request }`; `422 invalid_request` if an id does not exist on the wall |
| `GET /api/walls/:id/requests`              | `?status=open\|answered\|cancelled` | `{ requests }`                               |
| `GET /api/walls/:id/requests/:rid`         | `?wait=<ms>` (max 120000)       | `{ request }`; with `wait`, blocks while the request is open (long poll) |
| `POST /api/walls/:id/requests/:rid/answer` | `{ answer: <any JSON>, actor? }` | `{ request }`; `409 request_closed` if already resolved |
| `POST /api/walls/:id/requests/:rid/cancel` | `{ actor? }`                    | `{ request }`                                    |

In-process jobs use `ctx.walls.askUser(wallId, request, actor, signal)` (`apps/server/src/jobs.ts`), which opens the request
and resolves with it once answered; aborting the signal cancels it.

## Bank and other modules

The bank routes (`/api/bank/*`, `/bank/assets/*`) are owned by `packages/bank` (see `docs/bank.md`). Features owned by other
packages (omp bridge, draw backends, vision proxy, bank) plug into the daemon through `apps/server/src/modules.ts`
(`ServerModule`); they run after the loopback guard, so they inherit it.

### User elements (`/api/bank/user/*`, job `bank.user.import`)

Elements the user imported from a mesh (STL, GLB, 3MF). They are ordinary `BankElement`s with `source: "user"`, ids
`my-<slug>`, `provenance.origin: "user-upload"` and `license.redistributable: false`; the daemon merges them into
`GET /api/bank/index` (own ETag, search index, `/bank/assets/*`), so filters, search and the compatibility maths see them.
Zod contract: `packages/bank/src/user.ts`. Storage and conversion: `docs/bank.md` ("User elements").

| Method & path | Body / query | Response |
| --- | --- | --- |
| `GET /api/bank/user/elements` | | `{ elements: BankElement[] }` |
| `GET /api/bank/user/elements/:id` | | `{ element, meta: UserElementMeta }` (original file name, format, sha256, import settings, watertight/repaired, warnings) |
| `POST /api/bank/user/uploads` | `multipart/form-data` `file` (`.stl`, `.glb`, `.3mf`; 100 MB; extension and content are both checked) | `201 { upload: Upload }`: id, parts (triangles, bbox, watertight, guessed orientation), `defaultPartId`, `suggestedName`. Uploads expire after 24 h |
| `POST /api/bank/user/uploads/:id/preview` | `ConvertSettings` (`partId`, `orient {out, up}`, `anchor`, `unit`, `repair`; all optional) | `{ conversion }`: `glbUrl` (uncompressed GLB in the wall frame), `bboxMm`, `dimsMm`, detected `footprint` and `mountingCells`, `watertight`, `repaired`, `settings` (defaults applied), `warnings` |
| `GET /api/bank/user/uploads/:id/preview/<hash>.glb` | | the preview GLB |
| `DELETE /api/bank/user/uploads/:id` | | `{ ok: true }` |
| `POST /api/bank/user/elements/:id/reopen` | | `201 { upload, input }`: the stored original as a new upload plus the element's metadata as an import input (edit dialog) |
| `PATCH /api/bank/user/elements/:id` | any of `name`, `description`, `category`, `tags`, `toolClasses`, `fitsTool`, `footprint`, `mounting`, `printNotes` | `{ element }`; geometry untouched; a footprint edit drops pegs outside it |
| `DELETE /api/bank/user/elements/:id[?force=1]` | | `{ ok: true }`; `409 element_in_use` (`details.walls: [{ wallId, items }]`) while a wall places it, unless `force=1` |
| `POST /api/jobs` `{ kind: "bank.user.import", input }` | `UserImportInput`: `uploadId` and/or `replaceId`, `name {ru?, en?}`, `category`, `tags`, `toolClasses`, `fitsTool`, `footprint`, `mounting {kind, cells}`, `settings`, `id?`, `printNotes?` | `202 { job }`; `progress.message` is `converting`, `compressing`, `publishing`; the result is `{ element, conversion }` |

Errors: `400 invalid_body` (schema, mounting cell outside the footprint, footprint without `{0,0}`), `404 element_not_found` /
`upload_not_found`, `409 duplicate_element` (`details.id`: same geometry already imported) / `element_exists` / `element_in_use` /
`source_missing`, `413 payload_too_large`, `415 unsupported_media_type`, `422 mesh_unreadable`, `503 converter_unavailable`
(the bank python environment, `uv`, is missing). `replaceId` without `uploadId` re-converts the stored original (id kept).

## Client errors

The web app reports failures it survived (a missing GLB/thumbnail, a render error, an unhandled rejection) so they can be
diagnosed after the fact. Module `apps/server/src/clientErrors.ts`, behind the same loopback/origin guard.

| Method & path                  | Body / query                                                         | Response                         |
| ------------------------------ | -------------------------------------------------------------------- | -------------------------------- |
| `POST /api/client-errors`      | `{ kind, message, ts, url?, bankId?, status?, stack?, page?, userAgent?, detail? }` | `204`                |
| `GET /api/client-errors`       | `?limit=N` (default 50, max 500)                                     | `{ entries }`, oldest first, newest last |

- `kind`: `asset-load` | `render` | `unhandled` | `user-report`; `ts`: ISO timestamp; `detail`: flat `Record<string, string | number | boolean>`.
- Errors: `400 invalid_json` / `invalid_body` (unknown `kind`, missing `message`, bad `ts`), `400 invalid_query` (bad `limit`),
  `413 payload_too_large` (body above 16 KiB, refused without parsing). Responses are `Cache-Control: no-store`.
- Free text is truncated to `message` 2000, `url` 500, `page` 500, `stack` 4000, `userAgent` 300, `bankId` 200 characters; `detail`
  keys to 100 and string values to 500. `?query` and `#fragment` runs (they can carry tokens) are removed from every one of those
  fields, including URLs quoted inside `message` and `stack`, before anything is written. The scrub is blunt: text glued to a
  query (such as `:line:col` after it) goes too. `detail` keys that collide afterwards get a `#2`, `#3`, ... suffix (so a stored key may exceed 100 characters by that suffix).
- `ts` must be an ISO 8601 datetime (`2026-10-22T10:00:00.000Z`, offsets allowed).
- Stored as JSONL in `<home>/logs/client-errors.jsonl` by a single serialized writer; at 5 MiB the file is renamed to
  `client-errors.jsonl.1` (one generation kept). `GET` reads the current file, then `.1` if it needs more, and skips torn lines
  (a crash mid-append is terminated with a newline before the next entry).

| `POST /api/tools/drafts/:id/merge` | `{ keys: [...] }` | parts of one tool segmented apart (same photo) |

| `POST /api/tools/drafts/:id/add` | `{ photo, pointPx: [x, y] } \| { photo, boxXywh: [x, y, w, h] }` (photo pixels) | an object the segmentation missed, cut out by SAM2 from a click or a box and fitted like the others; new object `pending` in `{ draft }` |
| `POST /api/tools/drafts/:id/calibration` | `{ mmPerPx }` or `{ pointsPx, distanceMm }` | `{ draft }` back in state `created`: run `tools.analyze` again (tools already in the library stay marked). Refused (409) while the draft is being analysed |
| `POST /api/tools/drafts/:id/commit` | `{ keys?, tags? }` (default: accepted objects; `tags` are added to the tags of every committed tool) | `201 { tools, skipped: [{ key, reason }], draft }`; objects without a scale, unknown keys and objects already added are skipped with the reason; `409` unless the draft is `ready` (after a recalibration, analyse again first) |
| `DELETE /api/tools/drafts/:id` | | `{ ok }` |
| `POST /api/tools/drafts/:id/objects/:key/draw-view` | `{ views?: ("front"\|"side"\|"top"\|"back")[] (default `["side","top"]`: the end and the profile along the length, the two views a top-down photo lacks), backend?: "omp"\|"chatgpt-browser"\|"manual" }` (empty body = defaults) | `202 { job }` of kind `tools.draw_view` (a draw takes minutes; follow `GET /api/jobs/:id/events`). A **pinned** backend (body or the draw setting) that cannot run now is refused up front, no job queued: `409 { error: { code: login_required\|quota_exhausted\|challenge\|backend_unavailable, message, details: { backend, steps[], retryAfterMs? } } }`, `steps` being the literal commands (`omp login openai-codex`, `hsw-editor draw login chatgpt`). `400 invalid_body`/`invalid_json`, `404 draft_not_found`, `409 conflict` (object discarded/added), `400 invalid` (no cut-out). Docs: [draw.md](draw.md) |
| `GET /api/tools/drafts/:id/objects/:key/drawn` | | `{ views: DrawnView[] }`: the drawings kept for the object (newest per view, accepted or rejected), every one `source: "generated"` |
| `GET /api/tools/drafts/:id/objects/:key/drawn/<view>.<ext>` | | the accepted drawing (only names listed by the route above; `404` otherwise) |

Errors use the shape above; extra codes: `tool_not_found`, `class_not_found`, `draft_not_found` (404), `unsupported_media_type` (415), `invalid_request` (400, unknown class / preset, impossible edit), `conflict` (409, draft busy or already added), `vision_unavailable` (502: sidecar down, `HSW_VISION_URL`, default `http://127.0.0.1:8795`).

## Physics

Tools have mass and a centre of gravity, so they really hang. The daemon judges the tools of a stored wall exactly as the
editor does (maths in [physics.md](physics.md)): holders and board parts are the bank GLBs at the item's pose and dimensions,
tools are the generated class model (`gen:<class>` model ref or the item's `toolClass`, with the item's `params`) or the
user's library tool (`tool:<id>` model ref), each tool is judged on the holder named by its `parentId`, every other tool and
board part is an obstacle at its own pose. Read-only; `manifold-3d` is loaded on first use. Implemented in
`apps/server/src/physics/` (module `physics`), the agent tool is `wall_analyse_hang` ([omp.md](omp.md)).

| Method & path | Response |
| --- | --- |
| `GET /api/walls/:id/physics` | `WallPhysicsView` of the whole wall |
| `GET /api/walls/:id/items/:itemId/physics` | the same for one tool (`tools` has one entry; the other tools stay in its way) |

```ts
WallPhysicsView = {
  wallId, rev,
  tools: [{
    toolId, label: string | null, holderId,
    status: 'stable' | 'marginal' | 'unstable',  // hang status
    score: number,    // hang stability 0..1
    rating: number,   // hang score and removal convenience folded, 0..1 (hang counts twice)
    problems: [{ code, severity: 'error' | 'warning', params, text }],
    hang: { score, status, reasons, marginsG, massG, contactCount, penetrationMm, swingDeg, rest: { tiltDeg, position } | null },
    removal: RemovalReport | null,  // verdict free | needs_tilt | needs_two_hands | blocked, convenience, path, clearanceMm, ...
  }],
  flagged: number,   // tools with at least one problem
  skipped: [{ toolId, reason }],  // no_holder | holder_missing | no_model | no_physics
}
```

`code` is one of `levitating`, `penetrates` (not seated: stuck in the holder), `falls`, `tips`, `swings`, `slides_off`,
`needs_retention`, `overloaded`, `removal_blocked`, `removal_needs_tilt`, `removal_two_hands`; `params` carries the numbers
(`gapMm`, `depthMm`, `swingDeg`, `swayMm`, `marginG`, `neededG`, `massG`, `maxLoadG`, `blockedBy`, `path`, `reasons`). `text` is
one English sentence built from them (`describeProblemEn`), for example `Floats about 42 mm above its holder: nothing touches
it, so it would fall.`, `Swings freely (about 17° when bumped, about 40 mm sideways).`, `Needs two hands to take off: it is
heavy, there is little room for fingers beside it.`, `Cannot be taken off: blocked by i-7.`. The page has its own ru/en
catalogue for the same codes. A tool that overhangs the board edge is not a problem; only physics is judged. Bank elements
carry no per-slot load rating, so `overloaded` needs a `maxLoadG` the bank does not provide yet.

Items the analysis could not judge are listed in `skipped` (whole wall) instead of failing: `no_holder` (no `parentId`),
`holder_missing` (the parent is not a holder on this wall or its element is not in the served bank), `no_model` (a plain
box preset of a class without a generator), `no_physics` (the model carries no mass).

Errors: `404 wall_not_found`, `404 item_not_found` (unknown `:itemId`), `409 not_a_hung_tool` (the item is not a tool, or
the tool was not analysed: `details.reason` is the `skipped` reason), `400 invalid_id`, `405 method_not_allowed`.

## Settings

Per-user preferences (keymap overrides, palette recents, editor preferences). One JSON document per daemon user,
stored in `<home>/settings.json` (default `~/.local/share/hsw-editor/settings.json`); the daemon is its single writer.
The shared contract (zod schemas, limits, `applySettingsPut`) and the offline-first client live in
`packages/user-settings` (`@hsw-editor/user-settings`); import `createSettingsClient`, `createHttpTransport`,
`SettingsDocumentSchema`, `SettingsPutBodySchema` instead of re-modelling.

```
SettingsDocument = { schema: 1, rev: number, updatedAt: ISO string, data: { [namespace]: JsonValue } }
```

- `data` keys are namespaces (`keymap`, `settings`, `palette`, ...) matching `^[a-z][a-z0-9_-]{0,31}$`; at most 64.
  Each namespace holds one JSON value nested at most 16 levels deep (a scalar is depth 1). The serialized document is
  at most 256 KiB.
- `rev` starts at 0 and is +1 for every PUT that changes the document; a PUT that changes nothing returns the current
  document and does not bump it. Before the first PUT the daemon serves defaults
  (`{ schema: 1, rev: 0, updatedAt: "1970-01-01T00:00:00.000Z", data: {} }`) and writes nothing.

`GET /api/settings` -> the `SettingsDocument`.

`PUT /api/settings` body `{ baseRev?: number, data: { [namespace]: JsonValue | null } }` -> the new `SettingsDocument`.
Merge is per namespace: a listed namespace is replaced wholesale, `null` deletes it, unlisted ones are untouched. With
`baseRev` the PUT applies only if it equals the current `rev`; otherwise `409 rev_conflict` with
`{ error, settings: <current document>, currentRev }` and nothing is written. Without `baseRev` it is last-writer-wins.
Concurrent PUTs are serialized by the daemon.

The daemon itself reads one key of the `settings` namespace: `vision.segmentQuality` (`"fast"` | `"accurate"`), the default `segment.quality` of every vision stage request
(docs/vision.md, "Segmentation speed"); a missing or unknown value means the sidecar default `fast`.

| Status | `error.code`       | When                                                                              |
| ------ | ------------------ | --------------------------------------------------------------------------------- |
| 400    | `invalid_json`     | Body is not JSON                                                                  |
| 400    | `invalid_body`     | Bad namespace name, value too deep / not JSON, unknown key, more than 64 namespaces (`details`: issues) |
| 409    | `rev_conflict`     | `baseRev` is stale                                                                |
| 413    | `payload_too_large`| Body above 256 KiB, or the merged document would exceed it                        |

`GET /api/settings/events` (`text/event-stream`): `settings` event `{ rev }` on connect and after every accepted PUT, plus
a `heartbeat` every 15 s. A client that sees a `rev` above its own refetches (`client.notifyServerRev(rev)`), so a phone
and a desktop stay in sync.

Client (`createSettingsClient`): reads come synchronously from a `localStorage` mirror (`hsw-editor:user-settings:v1`),
writes land in the mirror at once and are pushed debounced and coalesced as pending namespace patches with `baseRev`.
On (re)connect it GETs the server document: namespaces with pending local edits keep the local value and are pushed,
every other namespace adopts the server value, so stale server data never overwrites an unpushed edit. A `409` refetches
and retries once. Offline (fetch fails) edits stay pending until the next `sync()`.

### Photo clean job and draw routes

`apps/server/src/photo-clean` registers the job `photo.clean` (`{ wallId, photoId, method: "auto" | "basic" = "auto", refresh = false }`) and
mounts `GET|PUT /api/draw/settings`, `GET /api/draw/backends[?probe=1]` and the manual-upload inbox of [draw.md](draw.md).
The job turns the photo's calibration into the board footprint (plus a 30 mm margin) in photo pixels and cleans that area:

1. **basic** (always, instant, offline): `fillWall` of `@hsw-editor/overlay` - a robust quadratic illumination surface fitted to the wall
   around the area, the rim deviation relaxed inward, matched grain; the variant is stored at once (`backend: "basic"`).
2. **AI** (`method: "auto"`): the draw backends in the user's `/api/draw/settings` order (`auto` = `omp`, then `chatgpt-browser`; `manual` is never
   used here) get the photo and a mask as two refs and an edit prompt; the answer is un-letterboxed, rejected when the unmasked part moved
   (`MAX_OUTSIDE_DRIFT`), else only the masked area (feathered) replaces the basic variant (`backend` = the backend id).
   `login_required` / `backend_unavailable` hand over to the next backend; `quota_exhausted` stops the chain.

Result: `{ status: "ok" | "current" | "needs_calibration" | "no_footprint" | "photo_not_found" | "stale", variantId, method: "basic" | "ai" | null,
ai: "done" | "not-asked" | "login_required" | "quota_exhausted" | "unavailable" | "rejected" | "failed" | "disabled", aiMessage? }`.
A variant whose footprint has not moved materially (1.5 % of the photo's longer side) is reused (`current`). The editor runs the job by itself
(debounced 1.5 s after the footprint settles) while the setting `autoCleanBackground` is on; the agent tool `wall_clean_background` and the
palette command "Clean the wall under the board again" run it on demand. Photos leave the machine only for the AI step.

### Vision jobs and routes

`apps/server/src/vision` registers the jobs `vision.photo_to_wall` (photos of a real wall only; a photo of tools only feeds the collection through `vision.photo_to_objects` / `tools.analyze`), `vision.photo_to_objects`, `vision.calibrate`, `vision.segment` and `vision.fit`
(inputs and results: [vision.md](vision.md)), plus `GET /api/vision/status` (never starts the sidecar) and `POST /api/vision/stop`.

## Static app

Everything else is the built web app (`apps/web/dist`): hashed `/assets/*` are `immutable`, `index.html`, `sw.js`
and manifest are `no-cache` (ETag, `304`), unknown paths fall back to `index.html` (SPA).

## On-disk layout

`$HSW_EDITOR_HOME` (default `~/.local/share/hsw-editor`):

```
walls/<id>/wall.json        snapshot (atomic write: tmp + fsync + rename)
walls/<id>/history.jsonl    one JSON entry per rev, appended + fsynced BEFORE wall.json is replaced
walls/<id>/photos/ models/  uploaded and generated assets (photos/derived/ for drawn views)
walls/.trash/               deleted walls
bank-user/                  user-made bank elements: index.json, glb/, thumb/, meta/, sources/, uploads/ (docs/bank.md)
settings.json               per-user settings document (atomic write, mode 0600; a corrupt file is kept as settings.json.corrupt-<ts>)
logs/client-errors.jsonl    client error reports (+ .1 after rotation at 5 MiB)
tools/<id>/                 user tool library: tool.json, model.glb, model-lod1.glb, thumb.webp, source/ (see tools.md)
tools/.drafts/<id>/         photo imports under review
server.lock                 pid of the single writer
```

The daemon is the single writer; the CLI and agents go through HTTP. After a crash the wall is rebuilt from
`wall.json` + the tail of `history.jsonl`.
